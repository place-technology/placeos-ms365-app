# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A PlaceOS Outlook task pane add-in POC, built from Microsoft's `outlook-add-in-sso-naa` sample. It uses MSAL.js **nested app authentication (NAA)** to silently get an Entra access token for the PlaceOS API scope, which will be exchanged for a PlaceOS token via `auth.cr` and used with the Staff API. `plan.md` holds the phased plan, key decisions, recorded tenant values and open questions. TypeScript, bundled with webpack + Babel (`@babel/preset-typescript`, so type errors do not fail the build). There is no test suite.

## Commands

```bash
npm install
npm run start          # dev server on https://localhost:3000 + sideload into Outlook (office-addin-debugging)
npm run stop           # stop debugging / unsideload
npm run dev-server     # webpack dev server only (no sideload)
npm run build          # production build to dist/ (rewrites localhost URLs in manifest to urlProd)
npm run build:dev
npm run lint           # office-addin-lint (eslint-plugin-office-addins); lint:fix / prettier also available
npm run validate       # validate manifest.xml
npm run package:app    # app bar app zip for ADDIN_URL (default placeos-dev); package:app:dev for localhost
# CI: .github/workflows/build.yml publishes dist/ (minus manifest.xml) to the build/prod branch on push to main;
# PlaceOS serves that branch as an Interface repo (folder outlook-addin).
# Per-customer packages in CI: .github/workflows/package-customer.yml (workflow_dispatch, input: domain)
npx tsc --noEmit       # type-check (not part of build; CI runs it, so keep it clean)
```

## Configuration

Customer onboarding (Entra registration, admin consent, `outlook_addin` authority config) is documented in `docs/entra-setup.md`. Hosting, per-customer packages, updates and when customers must redeploy are in `docs/deployment.md`. Local build/run instructions for humans are in `README.md`. Keep both in sync when auth, manifests or packaging change.

Auth config is **discovered per domain** by `src/taskpane/addin-config.ts` (`loadAddinConfig()`, cached) before MSAL starts. It reads `config.outlook_addin` (`client_id`, `tenant_id`, `scope`, `placeos_client_id`) from the public `GET /auth/authority`, and both the taskpane and the fallback dialog use it. `msalconfig.ts` exports `createMsalConfig(config)`; there are no static IDs. Development builds fall back to hardcoded test values when the domain has no `outlook_addin` (the UI says so); production builds throw instead.

- `client_id` must be the Entra client ID of an **OAuth source configured on the PlaceOS domain** (Backoffice). Otherwise auth.cr refuses the exchange with "no oauth strat on this authority matches the token audience".
- `placeos_client_id` is a separate PlaceOS application UID.
- auth.cr accepts v1 and v2 Entra tokens, so don't change the registration's token version.

The dev server proxies `/auth/` and `/api/` to `placeosDevDomain` (`https://placeos-dev.aca.im`) in `webpack.config.js`, so PlaceOS calls stay same-origin as in production. Keep the trailing slashes: `/auth` would also match `/auth.html`. It also proxies `/__map-proxy/<host>/…` to S3 hosts (`*.amazonaws.com`) only, because the floor plan buckets' CORS doesn't allow localhost; `floor-map.ts` uses it in development builds on localhost.

Only the add-in only manifest (`manifest.xml`) is used. The unified manifest configuration from the sample was removed.

## Two hosts, one codebase

* **Outlook add-in** (`manifest.xml`): task pane on read/compose mail and calendar events, pinnable. Entry `src/taskpane/taskpane.ts` (Office.js), page `taskpane.html`.
* **App bar app** (`app-package/manifest.json`, unified manifest): personal tab in the Teams, Outlook and Microsoft 365 app bar. Entry `src/taskpane/app.ts` (TeamsJS `app.initialize()`, NAA check via `nestedAppAuth.isNAAChannelRecommended()`). Page `app.html` is built from the same `taskpane.html` template, with the office.js script stripped by an html-loader preprocessor (`?app` resource query in `webpack.config.js`). Build the zip with `npm run package:app` (`ADDIN_URL`) or `npm run package:app:dev`; output goes to `dist-app/`. See `docs/app-bar-app.md`.

Both entries call `startApp(accountManager, hostLabel)` in `src/taskpane/app-ui.ts`, which holds all UI, token and PlaceOS logic. There are two views on the same page: **Today** (`#today-view`, the default, user-facing) and **Diagnostics** (`#app-body`, the original POC checks), switched by the header link or opened directly with `#diagnostics`. Diagnostics data checks only run when that view is opened. Today is loaded by `today-view.ts` / `today-data.ts` after the first successful PlaceOS token:
* `GET /api/staff/v1/events` for today (no filters = the caller's own calendar); rooms are events with a `system`, and visitors are attendees with `visit_expected`.
* `GET /api/staff/v1/bookings?type=desk|parking|visitor&include_booked_by=true&include_checked_out=true&include_deleted=true` (no `zones` = the caller's own bookings; never add `zones` without `user=current`). Status follows Workplace's `Booking.status`: cancelled (deleted), declined (rejected), ended (checked out or past the end), else open; cancelled and declined show a badge. Bookings of 12 hours or more show as "All day".
* Desk and parking names: `description` (HTML removed) → `asset_name` → `extension_data.asset_name`/`name`/`assigned_asset_name`; `parking.hide_selected_space` shows only "Parking". Otherwise, for asset-based desks/spaces (`asset_id` = `asset-…`), the name comes from `GET /api/engine/v2/assets/:id` (`name` || `identifier`); legacy metadata desk ids are shown as-is. `PlaceosLookups` caches zone and asset lookups. Location comes from the booking's zones (`level`/`building` tags) via `/api/engine/v2/zones/:id`, cached.
* Rooms show the level and building from `system.zones`, and "Declined" when the room declined.
* Visitors: guests with `visit_expected` on the user's events, plus visitor bookings. A booking with `linked_event` is skipped only when that event's attendees already show the visitor, because Book a room (as Workplace) posts meeting visitors as linked bookings only. Cancelled bookings with `extension_data.removed_from_group` are skipped.
* Desk and parking items have buttons (`TodayItem.actions`, rendered by `renderActions` in `today-view.ts`; confirmations are inline Yes/No because `window.confirm` doesn't work in add-ins, and the card reloads after an action). They follow Workplace's booking details: **Check in** from 15 minutes before the start until the end (`POST /api/staff/v1/bookings/:id/check_in?state=true`), **Check out** once checked in (`state=false`), hidden if `hide_checkin` is on in `desk.`/`desks.`/`bookings.` (`parking.`/`parkings.`/`bookings.` for parking), if `auto_checkin` is on in `desk.` (`parking.`), if the booking is declined, or for `unallocated…` parking; **Cancel** until the booking ends or is checked in (declined bookings too) (`DELETE /api/staff/v1/bookings/:id`). For recurring bookings only that occurrence changes (`/check_in/<instance>`, `/instance/<instance>`, using `booking_start` when there's no `instance`). Settings come from the booking's building via the shared `loadOrganisation` (`settingsForZones` in `app-ui.ts`; else the default building's settings, as Workplace uses the active building). The desk or space name is a link when its level (the booking zone tagged `level`) has a `map_id`: it opens the floor plan inline under the item (`toggleMap` in `today-view.ts`) with the desk (`extension_data.map_id` || `asset_id`, as Workplace's `viewLocation`) highlighted and zoomed in.
* **Next meeting** card: shown in the add-in's mail context (`taskpane.ts` sets `startApp`'s `showNextMeeting` for messages or no item, not calendar items) and always in the app bar app (`app.ts`). It shows the next non-cancelled, non-all-day calendar event that hasn't ended (any event, room or not), from today's events, else one extra events query for the next 7 days. The Join link only appears for `https://` URLs.
* **Book a room** (`#book-view`, opened from the Rooms card's button; open questions and unported features in `docs/room-booking.md`): a port of the legacy Angular add-in's room flow and meeting form (PlaceOS/user-interfaces `apps/outlook-addin`, `libs/events` `EventFormService.postForm`). PlaceOS creates the event (`POST /api/staff/v1/events`); it doesn't touch the Outlook item being composed. Flow: details form → free rooms (list or map, with filters) → confirm (catering, assets) → done.
  * Map view (`floor-map.ts`, legacy `interactive-map` / Workplace `space-map`): a List/Map toggle on the rooms step, shown when a searched building has levels with a `map_id` (floor plan SVG; parking levels excluded). One level at a time with its own picker (the Level filter is hidden in map view); the other filters still apply. Rooms are the SVG elements whose id is the system's `map_id` (else its id): green free, red busy, grey free but filtered out, colours from `explore.colors` like Workplace. Tapping a free room shows its details and a Choose button. The SVG (on S3, via the level zone's `map_id`) is fetched as text without credentials, so the bucket's CORS must allow the domain (a same-origin `map_id` would use `placeosApi(path, { text: true })`), sanitised (scripts, event handlers, animations and external links removed), its `<style>` rules scoped to `#bookMapCanvas`, and inlined; pan/zoom change the `viewBox` so it works in IE webviews.
  * `booking-settings.ts`: org, regions, buildings and levels, plus app settings. Settings resolve like Workplace's `SettingsService`: building app metadata, then region, then org `settings`, then org app metadata, then the legacy defaults. The app metadata name is the first of `outlook_app`, `outlook-addin_app`, `workplace_app` found on the zone. Keys are referred to without the `app.` prefix, e.g. `events.allow_assets`.
  * `room-booking-data.ts`: rooms (`/api/engine/v2/systems`), `room_booking_rules` (hidden rooms) and `events.bookable_hours`. Availability uses `/api/staff/v1/calendars/availability`, or room bookings with `events.use_bookings`. Also attendee search (`/api/staff/v1/people`), the event body, recurrence (`range_start`/`range_end`, weekday names, `nth_of_month`) and recurring clash checks (`/events/clashing-assets`). Event attendees include the room (`resource: true`) and have no `visit_expected`, as `postForm`. Linked bookings (visitors for external attendees, catering orders, asset requests) are posted one at a time with `event_id`/`ical_uid`. A failed booking is deleted from the organiser's calendar. If any of them fails, the new event is deleted.
  * `catering-data.ts`: shown if `events.catering_enabled` or `events.has_catering` (the legacy default is on) and the building has a menu. The menu is Assets: category `_CATERING_`, types `CATERING:<caterer>`. Lead-time rules come from `catering_config`; charge codes, required notes and `disabled_rooms` (no catering) from `catering-settings`. Items with `hide_for_zones` are hidden for those zones. Delivery offsets use `catering.step_interval` (default 5). There is one order per caterer. `app.catering_provider` limits the menu to that caterer. The menu has a search box and filters for caterer, categories and tags (items must have every ticked tag).
  * `asset-data.ts`: shown if `events.allow_assets` or `events.has_assets` is set. Free assets are a type's assets minus those in overlapping `asset-request` bookings. Rules come from `assets_config`; rooms in `assets-settings` `disabled_rooms` get no assets. There's a search box and a category filter.
  * Favourites: menu items and asset types have a star button that saves `favourite_menu_items` / `favourite_assets` in the user's `settings` metadata (`Organisation.toggleFavourite` / `saveUserSetting` in `booking-settings.ts`). Each section can show favourites only. Items with a quantity stay visible whatever the filters.
  * Recurrence is offered only with `events.allow_recurrence: true`, as Workplace. All-day meetings can't repeat daily unless `events.allow_daily_allday_recurrence` is set.
  * All-day bookings (`events.allow_all_day`, off by default): `allDayPeriod()` in `room-booking-data.ts` gives the whole local day, or `events.all_day_period` hours. As Workplace's `getAllDayTimeRange`, today's period doesn't start from now (desk, parking and visitor flows use it the same way). A whole day is sent as `all_day: true`; anything shorter as a timed event with `extension_data.custom_all_day`, as Workplace's `CalendarEvent.toJSON()` does. Both get `all_day_date` and no setup or breakdown. Duration limits don't apply; bookable hours do, in the building's timezone, as `postForm`. The Today view (`isAllDay` in `today-data.ts`) shows `custom_all_day` events and bookings as "All day" too.
* **Book a desk** (`#desk-view`, opened from the Desks card's button; `desk-booking-view.ts` / `desk-booking-data.ts`; open questions in `docs/desk-booking.md`): a port of Workplace's desk flow with `app.desks.use_assets`. Flow: date and time (or all day) → free desks (list or map, level and feature filters) → confirm → done. Desks are **Assets only** (no legacy `desks` metadata): asset type `_DESKS_` in the hidden category `_DESKS_` (read, never created), one `GET /api/engine/v2/assets?zone_id=<level>&type_id=…` per level of the building (or region with `use_region`). Name is `identifier` || `name`, `map_id` || id is the floor plan element, groups are `place_groups`, and `bookable` must be `true`.
  * Free = bookable, user in one of the desk's groups (if any), not hidden by the building's `desk_booking_rules` (matched against the level and the asset's `zones`), and not in `GET /api/staff/v1/bookings/booked?type=desk`.
  * Desk settings resolve `desk.*` → `desks.*` → `bookings.*` (`deskSetting`), as Workplace's `settingForType`: `all_day_period`, `bookable_hours`, `use_building_timezone`, `all_day_default`, `assigned_resource_booking` (`allow`/`deny`/`other_only`, default `other_only`: someone with an assigned desk can't book another, so when the view opens or the building changes, a desk asset in the searched buildings with `assigned_to` = the user replaces the form with their assigned desk and a **View on map** button that highlights it and zooms in with `FloorMap.focus`). Also `desks.allow_all_day` (default on), `min_duration`/`max_duration` (60/480), `desks.duration_step` → `bookings.duration_step` (30; parking always 15), `default_duration` (`desk.`/`desks.`/`bookings.`, 60), `desks.available_period` (90 days).
  * Before posting it re-checks the desk is still free and the user's own desk bookings for the period: `bookings.allowed_daily_desk_count` (default 1; 0 or less = no limit) and `extension_data.is_assigned` bookings. Then `POST /api/staff/v1/bookings` with `booking_type: "desk"`, `asset_id` = the asset id, zones org/region/building/level plus the asset's zones, `approved` = `bookings.no_approval`, and `extension_data` `assigned_asset_id`/`assigned_asset_name`/`map_id`. A whole-day booking is `all_day: true` ending 23:59.
  * The floor map reuses `FloorMap` with Workplace's `desk-` colour keys: green free, red booked, grey filtered out or not bookable by the user.
* **Book parking** (opened from the Parking card's button; open questions in `docs/desk-booking.md`): the same view, module and page elements (`desk*` ids) as Book a desk, opened with `openDeskBooking("parking")`. `ResourceKind` and `kinds` in `desk-booking-data.ts` hold the differences, and the view sets its text with `applyLabels()`. A port of Workplace's parking flow (`parking-flow`, `ParkingService`, `parking-assets.fn.ts`):
  * Spaces are Assets of type `_PARKING_SPACES_` in the hidden category `_PARKING_`, queried per level tagged `parking` (`isParkingLevel`); the map uses `org.mapLevels(ids, true)` and `parking-` colour keys. Rules are `parking_booking_rules`, availability `bookings/booked?type=parking`, the limit `bookings.allowed_daily_parking_count`. Spaces are bookable unless `bookable` is `false` (desks need `true`). Hidden category and type names match ignoring case and outer spaces.
  * Settings: `kindSetting(settings, "parking", key)` resolves `parking.*` → `parkings.*` → `bookings.*`; form settings (`formSetting`/`ownSetting`) read `parking.*` then `bookings.*`: `available_period` (7 days), `min_duration` 30, `max_duration` 480, `allow_all_day` (default on).
  * A plate number field, prefilled only for a user with a parking user entry: from their `plate_number` user setting, else that entry; required with `parking.require_plate_number`, sent as `extension_data.plate_number` with `user_groups` and `requires_manual_approval: false`, `title: "Parking Booking"`.
  * The building's parking users (`_PARKING_USERS_` assets, `zone_id` = building, `other_data.email`/`deny`/`plate_number`; `getParkingUser`) can deny a user. With `parking.restrict_home_location`, a user with an assigned desk in the building can't book parking there. Both show a message instead of the form (`showBlocked`); the building picker stays visible on the form and on that message.
* **Invite a visitor** (`#visitor-view`, opened from the Visitors card's button; `visitor-booking-view.ts` / `visitor-booking-data.ts`; open questions in `docs/visitor-booking.md`): a port of Workplace's invite visitor form for one visitor (`invite-visitor-form.component.ts`). One form (building, date and time or all day, name, email, company, reason defaulting to "Visit", plus pass number with `visitors.allow_pass_number` and an international tick box with `visitors.allow_international`) → done. Settings resolve `visitor.*` → `visitors.*` → `bookings.*` (`visitorSetting`): `bookable_hours`, `all_day_period`, `all_day_default`, `use_building_timezone`, `min_duration`/`max_duration` (30/240, 15 minute steps). With `visitors.reason_required` the reason has no default and is required. All day needs `visitors.allow_all_day` (else `bookings.allow_all_day`, default off). Dates go up to a year ahead.
  * Before posting it checks the user's overlapping visitor bookings (`GET /api/staff/v1/bookings?type=visitor&email=<user>`): the same visitor email can't be invited twice, and `bookings.allowed_daily_visitor_count` (default 1; 0 or less = no limit) caps them. Cancelled, declined, checked-out and ended bookings don't count, and if the query fails the checks pass, as Workplace. Then `POST /api/staff/v1/bookings` with `booking_type: "visitor"`, `asset_id` = the visitor's email, `asset_name` = name, `title`/`description` = reason, zones org/region/building, `attendees` = the visitor (`name`, `email`, `organisation`), `approved` = `bookings.no_approval`, and `extension_data` `visitor_name`/`company`/`international`/`pass_number`.
  * Past visitors are suggested under the name field from the `visitor-invitees` user setting (`email|name|company|international`, as Workplace), and the visitor is saved there after a successful invite (`Organisation.saveUserSetting`).
* **Add a room to an Outlook meeting** (`outlook-draft.ts`): when the add-in is open on a meeting being composed, `taskpane.ts` passes `meetingDraft` to `startApp`, and Book a room fills in that draft (time, subject, added attendees, room as an `enhancedLocation` Room on Mailbox 1.8, else as an attendee plus location text) instead of PlaceOS creating an event. The draft prefills the form. Notes, repeat, all day, catering, assets and visitors are hidden in this mode. It needs `ReadWriteItem` in `manifest.xml`. Details and open questions are in `docs/room-booking.md`.
* Times are epoch seconds, local midnight to 23:59:59. A 511 on events means PlaceOS has no delegated calendar token for the user. `AccountManager` takes an `AuthHost` (`isNestedAppAuthSupported`, `officeDialogFallback`). The Office dialog fallback is only enabled for the add-in.

Theming: `taskpane.css` defines colour variables for light, `data-theme="dark"` and `data-theme="contrast"`, each with a literal light fallback for IE-based Outlook webviews. `theme.ts` sets `<html data-theme>`. `app.ts` uses the TeamsJS `context.app.theme` and `registerOnThemeChangeHandler`. `taskpane.ts` infers the theme from `officeTheme.bodyBackgroundColor`, because Outlook doesn't support `isDarkTheme`, and listens for `OfficeThemeChanged`. With no host theme, `prefers-color-scheme` applies. Use the variables for any new colours.

## Auth architecture

Three webpack entries/pages (see `webpack.config.js`): `taskpane.html` (taskpane + polyfill chunks), `dialog.html` (fallback dialog chunk), and `auth.html` (no JS; it's just the MSAL redirect/popup target).

Token flow, all in `AccountManager` (`src/taskpane/authConfig.ts`). Methods return a `TokenResult` with `authPath` (`silent` / `popup` / `dialog`). Only `silent` counts as passing the POC's silent criterion.
1. `initialize()` creates a **nestable** PCA (`createNestablePublicClientApplication`) after `Office.onReady`.
2. On load the UI calls `acquireTokenSilentOnly()` (no UI). On success it immediately exchanges that token for a PlaceOS token and loads the PlaceOS data, so no clicks are needed. If silent sign-in fails it shows a Sign in button, which signs in interactively and then exchanges automatically. **Get PlaceOS Token** / **Refresh PlaceOS Token** remain for manual re-runs.
3. `ssoGetAccessToken(scopes)` is the full chain: silent, then `acquireTokenPopup`, then on `BrowserAuthError` `popup_window_error` (older Outlook clients can't open an `about:blank` popup) `getTokenWithDialogApi()`, which opens `dialog.html` via `Office.context.ui.displayDialogAsync`.
4. `src/taskpane/fallback/fallbackauthdialog.ts` runs inside that dialog. It uses a **standard** (non-nested) PCA with redirect flow and posts `{accessToken, username}` or `{error}` (`AuthDialogResult`) back via `Office.context.ui.messageParent`. `?logout=1` / `?close=1` query params drive the sign-out path.
5. Once the dialog fallback succeeds, its result promise is cached in `_dialogApiResult` and returned on every later call, so the scopes argument is ignored. The dialog always requests `defaultScopes` (the PlaceOS scope). The cached token is not refreshed when it expires.

Tokens are kept in memory only (`cacheLocation: "memoryStorage"`; only MSAL redirect state uses sessionStorage). Never write tokens to storage, the UI or logs. The one exception is `dev-raw-token.ts`, a hidden reveal/copy toggle gated by the `__DEV_TOOLS__` DefinePlugin flag (true only in development builds, so production drops it). PII logging is off. `dev-failure-tests.ts` (also `__DEV_TOOLS__` only) adds a panel that sends deliberately bad tokens to the exchange for the Phase 4 failure tests; it holds the first Entra token in memory for the expired-token case.

The sign-out button is only shown when NAA isn't supported (`NestedAppAuth` 1.1 requirement set) or the dialog fallback is in use.

`src/taskpane/token-inspector.ts` decodes the Entra token payload (no signature check) and checks `iss`/`aud`/`tid`/`scp`/`exp` against the registration, picking v1 or v2 expectations from the `ver` claim. The taskpane shows only these decoded claims.

`src/taskpane/placeos-helper.ts` has `placeosFetch` (same-origin JSON fetch with bearer token) and `exchangeForPlaceosToken`. That does the RFC 8693 exchange at `POST /auth/oauth/token` (PlaceOS/auth.cr, README "Microsoft Entra token exchange"), using `placeos_client_id` from the `outlook_addin` config: a PlaceOS application UID with no secret, not the Entra client ID. auth.cr returns generic error codes (validation failures are all `invalid_grant`), with details only in its logs. `refreshPlaceosToken` uses the PlaceOS refresh token at `POST /auth/token`. In `app-ui.ts`, `getValidPlaceosToken()` returns the cached token, then tries a refresh, then falls back to a new Entra exchange, as ts-client: parallel calls share one renewal, and a refresh token that PlaceOS rejects (4xx) is dropped. `placeosApi(path, init?)` wraps PlaceOS calls with that; on 401 it marks that token as expired (keeping its refresh token) and retries once; use it for new PlaceOS/Staff API calls. A string `init.body` is sent as JSON, and empty responses return `null`; `init.text` returns the body as text instead of parsing JSON. Engine list routes (`/api/engine/v2/zones`, `/systems`, `/assets`, `/asset_types`, `/asset_categories`) page with a `Link: rel="next"` header; pass `allPages` (from `placeos-data.ts`) as `init` to follow it and get every page as one array (only the link's query string is used, on the original path, up to 50 pages). The UI proves the token works by calling `/api/engine/v2/users/current`. Access and refresh tokens live in memory only.

`src/taskpane/placeos-data.ts` holds the Phase 5 read-only calls: the Staff API check (`/api/staff/v1/tenants/current_limits`), the authority, buildings, rooms and desks. Each takes a `PlaceosApi` function, so pass it `placeosApi` from `app-ui.ts`.

Shared pieces: `msalconfig.ts` (`createMsalConfig`), `msalcommon.ts` (`getTokenRequest`), `util.ts` (`createLocalUrl` resolves page URLs relative to the current page, because production serves the add-in from `https://<customer-domain>/outlook-addin/` while local dev serves from the root). PlaceOS calls (`/auth/…`, `/api/…`) stay absolute paths so they reach the domain root.

Production builds rewrite the manifest's `https://localhost:3000/` to `urlProd`, which is `ADDIN_URL` or `https://placeos-dev.aca.im/outlook-addin/` by default. There is one manifest per customer domain.
